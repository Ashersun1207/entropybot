# Manual routine reload recovery

This candidate starts at `a9238844935e3f39eda236f94f66c889f638154d` in the `manual-run-reload-recovery` worktree. It covers manual routine details, protected request identity and disposable verification fixtures. Parent review and serial integration remain separate.

## Recovery contract

A confirmed storage write can succeed while its immediate readback fails. The caller then receives an unknown result although the stored phase says confirmed. The original provider retained this uncertainty in memory, but a replacement provider or browser document could rotate the key. A confirmed phase alone therefore cannot prove that this caller observed a successful result.

The ledger format remains version 1, with at most 32 entries and 32,000 input characters. A fresh intent owner reconciles any existing marker, pending or confirmed, using its original key and context. Only a validated protected response and successful confirmed write/readback let that owner remember completion. Its completion map is bounded to 32 entries and checks key and scope. Capacity eviction is limited to confirmed markers this owner has reconciled; an unreconciled confirmed marker cannot silently disappear to make room. After a reload with 32 unreconciled entries, a new routine is blocked until an existing entry is reconciled and can be evicted.

Routine details restores the existing unknown-outcome explanation, Retry and Start another run from stored metadata. Retry explicitly selects recovery even if the same provider completed the operation while details was closed. The existing optional acknowledgement has three caller meanings: omitted permits a normal new operation after this owner's successful reconciliation; false explicitly recovers the stored operation; true intentionally replaces it after the existing confirmation. A new provider still recovers a stored marker when the argument is omitted. An acknowledged replacement does not cancel a prior server run.

After reconciliation, Run now deliberately creates a new key. Reopening details or reloading conservatively requires reconciliation again, including after an earlier successful response. This extra explicit Retry avoids guessing whether a prior document observed success. No request is sent merely by mounting or reloading. Unknown delivery, invalid provenance, storage failure and changed context retain the existing identity. The settings barrier, strict authoritative preflight, auth and protected-only POST remain in place. Late responses check the stored key and scope before confirming; they cannot overwrite an acknowledged replacement.

## Reproduction and executable checks

`src/state/routine-run-intent.test.ts` reproduces the successful confirmed write / failed readback, then discards the owner and compares actual POST keys. `src/state/routine-run-intent.integration.test.ts` mounts StoreProvider and the actual EventDetails controls, including replacement-provider recovery, late responses after unmount, acknowledged replacement, and closing/reopening details in the same provider. Bounds cover both refusal to evict an unreconciled confirmed marker and eviction of an entry reconciled by this owner.

The real browser recipe is `scripts/testing/routine-run-reload-ui.e2e.test.ts`, using the existing `mountPreview` and `launchVerificationServer` fixtures, the production EventDetails/StoreProvider, and the existing CDP connection/transport. Its small entry is `scripts/testing/routine-run-reload-preview.tsx`. It uses an existing Chrome, a disposable profile with mock Keychain/password-store flags, the repository fake engine, and loopback HTTP only. It does not install or build anything.

Run it with an existing Chrome executable:

```sh
OMB_UI_E2E=1 OMB_RELOAD_CHROME='/Applications/Google Chrome.app/Contents/MacOS/Google Chrome' node node_modules/vitest/vitest.mjs run scripts/testing/routine-run-reload-ui.e2e.test.ts
```

There are three browser cases: accepted response lost, confirmed write/readback failure, and accepted response held in flight until the document is discarded. Each waits for the first fake-engine run to complete, restarts the actual server with the same dataDir, executes Page.reload, waits for the new document, and uses the real Retry button. The same browser storage is retained. Before Retry succeeds, a real synthetic paired session supplies a changed authenticated context; the client refuses before POST and preserves the exact marker. Retry then returns the original key/context/run.id with one server run. A subsequent Run now uses a different key/run.id and leaves exactly two runs. The fixture separately traps any legacy run POST and requires zero fallbacks. Confirmation cancellation and absence of automatic POSTs on reload are also asserted.

Reports default to the persistent server log path with `.manual-reload.json` appended. Set `OMB_RELOAD_EVIDENCE_DIR` to an existing evidence directory for stable per-case report names. Reports include captured protected POST identities, original fixture URL/dataDir/log, zero legacy calls, assertion completion and close/removal observations. Teardown waits for browser and restarted server close and calls fixture.close; an unknown browser/server close retains the fixture directory. These observations do not prove every OS descendant or external resource has disappeared.

## Maintenance and security review

The product change is confined to the intent helper, the existing manual-run controls hook and the routine details uncertainty explanation. It adds no dependencies, credentials, new product network destinations, storage schema, timers, automatic retry, server authority or permissions. Persistent fields remain bounded, non-secret equality metadata. New tests and their browser profile are disposable; fixture reports intentionally retain synthetic request UUIDs and context hashes for comparison. No source size budget, correctness assertion or auth/settings barrier was weakened. Parent owns integration and any broader maintenance review.
