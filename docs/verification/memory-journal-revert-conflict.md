# Journal undo requires the recorded current state

Bounded product accuracy candidate from `d76d40da3ee5090e1b09071b4f5aef6989e3e173`, branch `codex/m1-journal-revert-conflict`. Main integration requires independent review. This changes whole-file undo accuracy; it does not implement general forgetting, retained-source deletion or cryptographic erasure.

## Contract and implementation

A journal undo succeeds only when the selected persisted row is internally consistent and the current document's existence and SHA-256 text hash match its recorded **after** state. Only created, edited and deleted kinds are accepted for undo. Created rows require explicit `before: null`, `beforeHash: null` and a valid 64-character lowercase hexadecimal afterHash. Edited/deleted rows require a string before, a valid beforeHash equal to the hash of that retained string, and a kind-appropriate afterHash: valid non-null hash for edited, explicit null for deleted. Created/edited rows require an existing document; deleted rows require absence. Missing, malformed or contradictory metadata is refused rather than inferred from current bytes. Empty strings remain valid retained versions; an empty existing file is different from absence, although both have the empty-text hash.

`server/memory-journal.ts` checks this before preparing an undo and passes the same expected state to the actual store write/delete. `server/memory-store.ts` checks again after its own read, immediately before synchronous mutation. Checked writes avoid `ensureWorkspace`'s unrelated core-file seeding; a missing core file must remain missing on conflict. Existing callers without the optional expectedState preserve their write/delete behavior, including the editor's existing expectedHash conflict contract.

Stale or inconsistent undo returns 409 with a fixed instruction to reread and review. The ordinary journal reader still returns recognizable malformed rows; undo validates the selected row instead of silently hiding it and returning 404. Existing canRevert=false imported, sensitive and over-cap rows retain their earlier 400 unavailable refusal before consistency checks. Consistency failures include no retained/current document text, provider details or private path. The HTTP route retains its existing `{ error }` shape. It does not append a revert row or advance journal baselines. Successful latest undo still appends an ordinary attributed revert row, and undoing that revert follows the existing audit chronology. There is no forced historical overwrite, semantic matching, restore policy schema or cleanup of historical copies.

These checks and mutations are synchronous in the current single-process server. The route's journal flush is awaited **before** the revert checks. There is no await between the final store check and mutation. This is not OS atomic compare-and-swap: other processes, native/injected filesystem reentry after the final read, symlink races between checks, or ABA changes returning to the same bytes/existence are outside the guarantee. Existing path allowlists, symlink checks, secret redaction, capacity limits and HTTP authorization remain in force.
