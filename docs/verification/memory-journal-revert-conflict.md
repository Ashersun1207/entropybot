# Journal undo requires the recorded current state

Bounded product accuracy candidate from `d76d40da3ee5090e1b09071b4f5aef6989e3e173`, branch `codex/m1-journal-revert-conflict`. Main integration requires independent review. This changes whole-file undo accuracy; it does not implement general forgetting, retained-source deletion or cryptographic erasure.

## Contract and implementation

A journal undo succeeds only when the current document's existence and SHA-256 text hash match the selected row's recorded **after** state. Created/edited rows require an existing document and a valid 64-character lowercase hexadecimal afterHash. Deleted rows require explicit `afterHash: null` and an absent document. A missing or malformed afterHash is refused rather than inferred from current bytes. An empty existing file is different from absence, although both have the empty-text hash.

`server/memory-journal.ts` checks this before preparing an undo and passes the same expected state to the actual store write/delete. `server/memory-store.ts` checks again after its own read, immediately before synchronous mutation. Checked writes avoid `ensureWorkspace`'s unrelated core-file seeding; a missing core file must remain missing on conflict. Existing callers without the optional expectedState preserve their write/delete behavior, including the editor's existing expectedHash conflict contract.

Stale undo returns 409 with a fixed instruction to reread and review. It includes no current document text, provider details or private path. The HTTP route retains its existing `{ error }` shape. It does not append a revert row or advance journal baselines. Successful latest undo still appends an ordinary attributed revert row, and undoing that revert follows the existing audit chronology. There is no forced historical overwrite, semantic matching, restore policy schema or cleanup of historical copies.

These checks and mutations are synchronous in the current single-process server. The route's journal flush is awaited **before** the revert checks. There is no await between the final store check and mutation. This is not OS atomic compare-and-swap: other processes, native/injected filesystem reentry after the final read, symlink races between checks, or ABA changes returning to the same bytes/existence are outside the guarantee. Existing path allowlists, symlink checks, secret redaction, capacity limits and HTTP authorization remain in force.

## Reproduction and regression entry points

All data is synthetic, in suite-owned temporary homes or `launchVerificationServer` disposable workspaces, using the existing fake engine. No live data, Keychain, model/provider calls, dependency installation, app build, installation or push is involved. Dependency reuse is a local node_modules symlink to the assigned engineering foundation installation, under Node 24.22.2. Default short canonical macOS temporary paths are retained.

- `server/memory-revert-conflict.test.ts`: actual journal writes, flush and revert for A→B→C, created topic/core followed by edits, deletion followed by recreation or empty-file recreation, missing documents after edits/creation, malformed/missing expected hashes, and imported-row refusal. Actual core creation uses `journalTurnWrite` around a real fixture file write: ordinary save seeds MEMORY.md and therefore cannot simulate this creation faithfully. Existence/hash conflicts preserve exact document and journal bytes, indexed documents, synthetic vectors and warmed bigram search results. An owned fs mock inserts changed bytes after successful earlier reads, including after the store write's preparation read, proving mutation checks are effective. Latest core undo and undo-of-revert remain positive.
- `server/memory-routes.test.ts`: isolated full server HTTP writes and flush-through-journal reads, six stale-state cases, exact file/journal-byte equality, fixed refusal response, latest undo and undo-of-revert chronology. Per-case hashes are emitted in test output. The existing topic/log/path/legacy route and fake-engine turn assertions remain.
- `src/components/bot-settings/MemorySection.revert.test.ts`: mounted actual MemorySection and real client API helper against synthetic HTTP responses; clicking Undo displays the 409 message, keeps the current editor, re-enables Undo and makes no follow-up write or restoration announcement.
- Existing `server/memory-journal.test.ts`, `server/memory-store.test.ts`, `server/routes/bot-memory.test.ts`, `server/memory-layer.e2e.test.ts`, team-memory and embedding-index suites retain latest undo, redaction, path/symlink, scoped HTTP/layer and memory workflow coverage. Existing component/list/client suites remain in the bounded final combination.

One original core creation test recorded after=`hello` but only called ensureWorkspace, leaving seed bytes on disk. The new safety contract correctly rejects that mismatched fixture. The unchanged original test and its failure are preserved externally; the fixture now writes its recorded after bytes before undo, retaining every original deletion/empty-text assertion. No original test was found to intentionally require overwriting unrelated newer facts.

The first HTTP matrix preparation failed because a newly created bot need not have a seeded MEMORY.md yet. This was a fixture assumption, not a product failure. The repaired HTTP matrix covers topic paths; actual core creation is covered through the real journal wrapper described above. The failed run is retained; no product check, timeout or assertion was weakened.

## Evidence, maintenance and limits

Receipts and logs live in the controller's private `engineering-foundation-evidence/m1-journal-revert-conflict/` directory. Each run records exact argv, Node/dependency location, runner hash, UTC bounds, exit code, pre/post HEAD/tree/status and tracked/untracked source hashes. Frozen final runs also archive relevant exact source/test/docs/lock/runner bytes and diffs. Red baseline source is bound to the original Git blobs, not the later candidate. JSON reports retain failed assertions and filtered tests; filtered baseline reproductions are not called complete suites. Final counts and candidate SHA/tree are in the external handoff report, avoiding a post-check documentation change.

The initial synthetic baseline reproductions returned success instead of refusing stale changes; the HTTP reproduction returned 200 rather than 409. A later corrected baseline run includes faithful core-creation fixtures and the store-boundary interleavings. The final bounded combination includes journal/store/routes, the mounted settings UI, isolated full-server memory workflows, relevant scope/layer and embedding regressions, size/docs guards, strict server/app types and scoped lint. Only completed exit-zero receipts establish a passed check; fixture close and journal flushing are part of the tests, not inferred from an idle session or file existence.

Maintenance/security review follows journal selection → preflight → store boundary → journal append and HTTP/client error handling. Product changes are confined to the journal and store. No dependency, installation script, network request, provider/model choice, persistent schema, permission, UI design or arbitrary file operation is added. Conditional deletion retains the existing core-file prohibition and path guards. Conflicts return before recording a change; existing retrieval/embedding code is unchanged and projection preservation is asserted with synthetic data. This is a scope review, not a full-repository or cross-platform security certification. macOS synthetic/isolated-server evidence does not prove OS-level concurrency, forensic erasure, real-model behavior or release readiness.
