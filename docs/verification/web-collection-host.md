# Synthetic collection host seam

Baseline: `2e3a7a8e9`, branch `codex/engineering-collection-host`, sole writer in `.worktrees/engineering-collection-host`. This slice adds only the inline reader, host adapter, adjacent test and this document. Parent review and serial integration remain pending.

`readInlineCollectionPage` implements the existing `CollectionOptions.read` contract: it accepts a source, cancellation/deadline signal and finite UTF-8 byte allowance (1–1,000,000). It rejects missing inline HTML, oversized text and cancellation, returns literal text, and performs no transport, parsing or execution. A string-length check rejects plainly oversized input before measuring UTF-8 bytes. The source string is already allocated by the caller; this reader creates no response buffer. collectWeb supplies its existing finite deadline signal and bounds the awaited read. Standalone callers must supply their own finite timeout signal; this immediate reader has no timer or asynchronous transport to cancel.

`hostWebCollection` accepts an existing RoutineRun, stable request identity, immutable plan, exclusively owned private output root, reader, signal and injected publication callback. It calls real collectWeb unchanged, then constructs at most 4096 UTF-8 bytes of plain text containing page count, unique count, JSON-escaped literal path and SHA-256. Page content is never included in the summary. It does not change RoutineRun status, runtime storage, message rows, routine schema or production dispatch. Authentication, destination authority, stable request/run identity and callback message rendering remain the eventual caller's responsibility. The plan/options must stay immutable for the invocation.

Publication uses the existing command-receipt database, with a separate `web-collection.publish.v1` namespace. The key hashes routine/run identity; receipts additionally bind request identity, exact report and summary. collectWeb validates the original plan and artifact on every call before publication replay. No callback executes inside a SQLite transaction. A durable reservation precedes the callback; a completion receipt follows only its successful resolution. Confirmed completion skips subsequent callbacks, including after reopen. Concurrent or resumed reservations without completion refuse with an explicit unknown-outcome error. A callback rejection propagates and leaves collection artifact completion intact, without claiming publication success.

This provides one callback invocation for an admitted publication, and one confirmed publication in the successful fixture. It cannot promise exactly-once external delivery: a crash before callback invocation can leave zero publications, and a callback may accept an effect before rejecting or before completion is stored. These windows conservatively require reconciliation rather than resend. There is no automatic repair, second scheduler, retry workflow or new database. The callback must resolve only when publication is confirmed, honor its signal, and bound its own work; the adapter does not forcibly terminate an arbitrary publisher.
