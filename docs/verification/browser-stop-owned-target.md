## Ownership and cancellation contract

URL uniqueness cannot establish tab identity. The old helper read a current URL, listed CDP targets later, and attached to the unique matching URL. If A moved from U to V and B became the only U, cancellation could stop and blank B.

The default legacy engine's existing session boundary now runs `tab list --pin-tab` before dispatch, within the existing browser lane. It accepts exactly one active tab with a `targetId`, then obtains the same session's local CDP endpoint. The helper attaches only to that target ID; URLs never participate in target selection. Missing, malformed, duplicate-ID, oversized, or vanished targets cannot select a substitute. The native pin is sticky: after target disappearance, the engine refuses fallback to another tab; explicit tab selection/new-tab operations remain the engine's own behavior. No second tab registry or session manager is introduced.

This uses the existing packaged agent-browser 0.37.0 protocol and resources. The packaged `tab --help` documents stable target IDs and sticky pin behavior. The isolated `protocol` probe observed two same-URL tabs with distinct IDs, closed the active pinned target, and observed the following open fail while the other target remained. No upstream source archive was available in the inspected local source paths; no download, rebuild, or upstream patch was performed. The resource/protocol evidence is not a source audit of all upstream behavior.

Each cancellation invocation has a private operation fence. Original RPC settlement invalidates it; cleanup completion or its timeout also invalidates it. Before each page command, including after the `Page.stopLoading` acknowledgement, the helper checks this fence, the runtime's ownership/closing/uncertainty state and the original call deadline. A pending human takeover invalidates cleanup immediately. The existing lane stays held while cancellation is awaited; unconfirmed cleanup preserves the existing lost-call gate. A subsequent recovery read can establish that the earlier command ended, but does not execute or replay the requested new action.

The helper sends `Page.stopLoading`, then, only while its operation remains current, `Page.navigate` to `about:blank` to release an engine navigation waiting for a load event. A successful navigate response must contain a frame ID and no `errorText` or download result. Protocol errors, disconnects, missing responses and timeouts cannot silently become successful cancellation. Stop acknowledgement is bounded at 1500 ms and original RPC draining at a further 1000 ms; a late acknowledgement cannot trigger another page command after cleanup is invalidated. An acknowledged command already sent to Chrome cannot be recalled.

The interrupt route propagates the request's abort signal through the runtime router. Existing capability checks continue to prevent queued or late old-turn work from dispatching. Cancellation does not undo a site's accepted requests. It never kills Chrome or closes unrelated tabs to free the lane. The new cancellation path excludes `attachesToChrome` sessions, including My Chrome; it makes no broader cancellation claim for that path or for the native Chrome engine.
