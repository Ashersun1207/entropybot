## Proposed identity and trust contract

Introduce a host-owned accepted item **before** either derivation is written:

```text
SourceKey = (workspaceNamespace, trustedPersonScope, sourceItemId)
SourceVersion = (SourceKey, positiveInteger revision)
AcceptedItem = SourceVersion + accepted body + host source receipt
NoteDerivation = SourceVersion + layer/path + noteItemId/noteRevision + exact document/span receipt
ProfileDerivation = SourceVersion + learnedFactId/factRevision + exact profile/span receipt
```

`workspaceNamespace` is a host-persisted random namespace, not a hostname, email, model field or current session ID. Desktop uses the local owner within that namespace; Team uses the existing server-derived person key. `sourceItemId` is a host random UUID minted once after admission; `revision=1` initially. The namespace prevents a copied UUID from silently joining a different workspace/person. A card UUID remains a projection ID; it is not reused as the source ID. Two facts from the same turn receive distinct source IDs even if bot/time/evidence quote are identical.

The source receipt records trusted layer, thread, stored turn/message references where available, and the capture operation/candidate ordinal. A validated source span may be recorded as offsets and a digest of the corresponding immutable input snapshot. A digest or quote proves which bytes were accepted; it does not prove the model's sentence is true, atomic or semantically equivalent. Never upgrade a guessed `attribute` result to a verified exact source. Ambiguous attribution remains notes-only for A.

**Host-validated handle** means an internal, non-JSON value issued by the acceptance coordinator, bound to the current operation, person, item and revision, then to read-back committed note bytes. The profile writer must validate it against that coordinator/store, not merely accept an object with those fields. A TypeScript brand alone is insufficient at runtime. Keep construction private; an operation-local registry/object identity check can validate live handles. Rehydrating durable references is a host-only path with version/schema/scope/document checks, not the model parser or HTTP body parser.

**Model-claimed source** means `from`, `evidence`, `noted`, a copied ID/opaque string, JSON fields called `sourceItemId/person/revision`, or text pretending to be a handle. None authorizes a join. No first-slice IDs or handle selectors need to be exposed to the model. Do not accept an existing ID from a candidate to attach a new profile rendering to another item. The host always mints the new identity and binds it to the exact accepted candidate instance used for both writes.

## Establishing the common item without a matching oracle

The smallest sound creation path takes one admitted **new** Candidate, freezes one accepted body, and uses that body for both notebook and learned line. It does not ask a second helper to find or translate the corresponding profile item. Notebook date/source formatting and the learned-by prefix differ, but both are deterministic renderings of this same accepted body. Capture may already have rendered Chinese speech in English; this design requires no translation and makes no promise about its quality. A later full-item notebook correction can use Chinese text because traversal uses the stored ID, not the languages of either body.

Admission and ordering for this path:

1. Preserve existing visibility, owner/evidence, secret handling and profile fences. Resolve trusted person before reading any new linkage store. An unresolved or no-person scope cannot acquire a profile link. Shared/room notes continue under current note policy.
2. Select new, bounded, single-line candidates with sure conversation attribution and available trusted source references. `noted:true`, duplicate/deduped, truncated/unsupported, independently pre-existing note, restored provenance that cannot be validated, and model-requested existing-item associations are ineligible for A. Do not infer a note handle from text equality even if it is byte-identical.
3. Normalize/redact once before freezing the accepted body; if either sink would further truncate or otherwise change that body, withhold the combined item rather than silently claiming equivalence. Apply current suppression for admission as today, without adding any new suppression identities.
4. Mint a fresh source ID and revision before the fork. Pass the accepted item through filing, preserving candidate/operation identity rather than using `.find(text)` or an array position after filtering. Write the planned full note span; read back exact bytes. Only that success yields a committed note handle.
5. Pass structured learned inputs containing that committed handle. The profile planner may reject a duplicate/limit/suppressed body. That leaves a valid notes-only item with no About me edge; it must **not** attach to an older equal-text profile line. Learning produces its own fact ID and returns an exact committed profile receipt.
6. Publish the derivation edge only after all referenced note/profile/card bytes have been confirmed and the person linkage state is persisted. A failed or uncertain phase leaves notes-only/unresolved or partial status; it never manufactures an active link from a count of learned facts.

The host can guarantee common operation identity and whole-item derivation. It cannot prove that a generated sentence contains one logical proposition. Do not introduce a semantic or punctuation classifier to pretend otherwise. For the initial creation slice, a compound sentence is at most one indivisible item; it confers **no permission for later clause surgery**. Automatic correction eligibility for compound or independently rendered bodies is withheld until a separately accepted full-item contract exists. Where atomicity cannot be established under that contract, use B's explicit complete profile replacement or remain unresolved. This limitation is fundamental, not solved by adding evidence IDs.

Recommended host metadata location: a new owner-private, versioned **person linkage sidecar**, outside model-readable notebook files. A sidecar record contains the namespace, schema version, source item/current revision, accepted-item origin receipt, note item/revision with layer/path/document hash and exact full-span offsets/hash, and optional learned fact ID/revision with profile hash/full-line span receipt. The Team record includes the learned row's text/line/bot/name/time because no desktop card is persisted there today. Desktop card source fields are a checked projection of this state; they are not an independently trusted second graph. An external edit, unsupported writer, move, duplicate, deletion or missing/corrupt sidecar yields unlinked/conflict. Do not relocate by line number, scan for the old body, or accept a pasted Markdown marker as identity. Conservative whole-document invalidation sacrifices coverage but is a safe first implementation choice.

Profile lines also need a version-bound exact receipt: card ID alone does not locate a current line in the plain profile. Do not scan for card text after manual edits or eviction. ## Later correction traversal — separate implementation slice

A future A correction must resolve **one current complete note item**, not a semantic fact or an arbitrary matching subpassage:

1. Resolve active capability/layer/person as today, then validate the note handle against that person's state, expected item revision, exact current document receipt and complete span. Ordinary `oldText` can continue to edit notes, but a unique substring does not qualify for A traversal. Do not read another person's store when a selector is missing locally.
2. Require exactly one active recorded profile derivation for the same source item and source revision, with a supported whole-item replacement contract. Missing/multiple/stale edges, compound partial requests, independent translations/paraphrases or manually altered lines remain unresolved. There is no fallback to body/date/bot/evidence/turn matching.
3. Resolve the learned fact ID **inside that same person's store**; validate fact revision and exact profile/span receipt. Preserve original ID, author/name/time and learned prefix. A copied UUID from another person cannot authorize a read or write. Duplicate visible lines cannot override the recorded span; an unvalidated duplicate invalidates the document receipt.
4. Preflight both complete new renderings/limits. Keep the source item ID, increment its source revision; update note/fact revisions and the exact derivation receipts. Supersede leaves the old note revision as historical and appends the new note revision under the same source item; the struck row is never the active target. Do not follow unrelated mentions of the old value.
5. Report saved notes and exact profile outcome separately. Preserve current person fence invalidation around correction; item revisions add durable provenance, not universal replay suppression. If notes succeed and profile/metadata fails, mark the edge inactive/partial and return that state. Never roll back unrelated documents or retry supersede blindly.

For a linked whole item, the replacement body can be used verbatim for both derivations under an explicit whole-item request. This needs no forced translation. Producing a separate profile paraphrase requires a new accepted derivation operation, not matching the generated text to some older line. An existing compound profile (color plus cats) cannot be modified by selecting only its color clause; without complete replacement preserving the whole selected item, defer to core B or unresolved. The host does not claim to verify semantic preservation of an arbitrary model-provided whole replacement.

The key supplies identity only. A fresh helper reading retained history can still create a new unlinked or newly minted assertion with the old meaning. No global tombstone/suppression, replay search or persistent semantic forgetting is introduced. Retained historical revisions and item status are provenance, not a general policy for blocking similar future text.

## Partial writes, restart and compatibility

Current file renames do not provide a transaction across notes/config/cards/person metadata. The first A slice must publish an active edge last and require every referenced current receipt to validate at use. Failed note write: no profile learning for that item. Note saved/profile rejected: notes-only. Profile saved/card or linkage write failed: partial/unlinked; do not claim prevention for that item. Notification failure after durable commit does not repeat mutations. Missing/corrupt linkage storage is unknown, not an empty validated graph.

An interrupted creation can leave note/profile text without a usable edge. That is acceptable only as an explicit limit: startup must not auto-link those rows by text. Persisting an inactive creation record before writing and activating it last is a possible implementation; automatic crash reconciliation/idempotent retry is not required by this design's first-slice claim. Repeating an uncertain creation cannot adopt an old same-text fact; it remains unresolved. Pending restored turns carry no accepted item identity today; do not restamp them as verified new source work. Preserve the current process-local fence and restored-origin observability.

A person-scoped sidecar is the recommended storage design because it preserves current Team profile v1 and can fail closed on separate-write mismatch. It does not solve cross-file atomicity, malicious local filesystem writers, cross-process races or ABA. Those must not be implied by calling a handle “validated.”

## Recommended first slice and acceptance criteria

Assign **new capture item creation only**, with host IDs minted before the fork, successful note handles gating structured learn, and persisted person-scoped derivation receipts. No correction traversal, new tool selector, semantic helper, dream association or legacy repair. Start with same frozen body for both renderings, single-line candidates, sure source/person attribution and new notes only. If the controller cannot assign both person stores and the writer-invalidation/compatibility boundaries, do a read-only eligibility projection first; do not ship a half-persisted “linked” flag.

Primary implementation files would be `server/memory-capture.ts`, `server/memory-upkeep.ts`, `server/workspace.ts`, `server/about-me.ts`, `server/profile-learned.ts`, `server/people-about.ts`, `server/host/cloud-team-host.ts` and callback wiring in `server/index.ts`. Keep new identity/storage logic in one focused host module rather than duplicating it in each sink; its filename is an implementation choice. Existing writer paths need receipt invalidation coverage before links are called usable. Dream must use an explicitly unlinked adapter and must not manufacture a handle from its conversation/line indices. Prefer/append outside this unified capture path retain existing unlinked behavior.

Fallback: an A-ineligible candidate may retain its ordinary notebook write. It receives no A-linked profile addition and a fixed reason such as `source_unresolved`, `existing_note_unlinked`, `note_not_committed` or `profile_not_committed`. Legacy rows/dream/other unlinked callers remain explicitly unlinked under their existing learning policy. For later corrections, use current core B exact pair under existing authority, or notes saved/About me unresolved when no pair is supplied. Do not invent automatic profile success.

Future implementation acceptance must inspect actual persisted bytes and fresh host/model projections, using synthetic fixtures only:

1. One new owner candidate creates one source ID/revision before writes; note receipt, new learned record and person state agree. Deterministic prefixes differ but accepted body is the same. Reload validates the link; no ID leaks into model-facing profile/notebook text.
2. Two candidates from the same turn/bot/time/evidence produce distinct IDs and exact separate edges. A note failure or duplicate for candidate A cannot pair A's profile body with candidate B's successful handle. Topic/core paths preserve candidate identity through filtering.
3. `noted:true`, legacy text, ambiguous `from`, missing trusted source references, temporary facts, truncation/redaction mismatches and note write/capacity failure yield no A edge. No attachment to an existing equal-text profile line. Profile dedupe/limit rejection leaves the note with no profile edge.
4. Desktop uses only the owner store. Two Team members may each learn identical bodies under separate scopes; one cannot lookup/read/mutate the other's store. Actual room/shared captures remain notes-only. Team linked rows persist without writing global desktop cards. Unknown scope cannot later become valid; existing fence tests remain intact.
5. Change a note/profile through an unsupported writer, B correction or settings, move it by tidy/archive, evict its only card, or provide missing/corrupt metadata: read validation returns unresolved, without scanning/relinking. Coherent supported reload is positive; incomplete backup/import/cloud-send is unlinked. Version-1 Team profiles remain readable.
6. Inject note, profile, card, sidecar and notification failures at their actual boundaries; inspect saved bytes and edge activation. Partial status is truthful and retry does not silently attach to old text. No claim of crash recovery from a fake successful callback.
7. Exercise remove-learned-fact through its existing route with the profile line present and already absent; the latter must invalidate even though no profile-save callback runs. Remove → reload → journal undo of a note change or manual restoration of exact old note/profile text must leave the edge inactive/unresolved, even when document hashes match again. Inject partial card/linkage metadata failure around removal; assert durable invalidation or refusal before side effects, no resurrection after reload/restoration, unchanged notebook bytes from removal itself, no recreated card and unchanged existing removed/forgotten policy semantics. This is lifecycle acceptance, not automatic correction acceptance.
8. No correction behavior is added in this slice: original unqualified Chinese/English case remains unlinked; explicit core B still reports and operates as today. Negated cyan, unrelated cats, another person's cyan and independently paraphrased facts are never joined by vocabulary.

### Bounded model-forgery negative test specification

This is a **proposed offline test**, not executed production acceptance in this research. Use one disposable owner/person store, a fake capture helper and actual parser→acceptance→filing→learn boundaries after implementation. Preseed item A (color) and unrelated item B (cats), plus a second person's same-text item. Record exact bytes of all stores; instrument person-store access so even a foreign read fails the test.

Return at most eight synthetic proposals covering: (1) forged `sourceItemId` naming A, (2) valid-looking copied handle JSON naming B, (3) another person's ID/person key, (4) stale revision, (5) `noted:true` plus a claimed handle, (6) altered text with a known ID, (7) A's genuine internal handle replayed under a different candidate/operation in a controlled host call, and (8) one ordinary new candidate positive control. Candidate text can literally contain fake JSON/Markdown IDs. Fake model output never receives the genuine internal handle object.

Choose **reject-claimed-host-fields-for-this-proposal**, consistently with the A parser contract above. Proposals (1)–(6) carry reserved host fields and are rejected as whole proposals before note filing, ID minting or profile learning; they produce no new edges. This includes the otherwise eligible new body in (6): dropping the forged field and creating a fresh item is not permitted for that proposal. Direct structured-learn attempt (7) is rejected for a reconstructed/copied/wrong-operation handle even when UUIDs and text are valid. Assert no supplied ID is adopted, no pre-existing edge is changed, A/B and foreign-person records remain exact, and foreign store access count is zero. Proposal (8) must create its intended edge with a fresh host ID and coordinator-issued validated handle. Add a separate second positive host control under a new valid operation, outside the eight-proposal batch; it must create a second intended edge to show rejection is not a blanket learn failure. Exactly these two positive controls create new edges. Fake IDs appearing only inside ordinary candidate text are inert text, never parsed as handles or authority; this does not require substring filtering. Finite fixture and calls only; no new global exclusion list. This establishes that model-supplied strings cannot manufacture a link, not that a model cannot propose an incorrect fact.

For the later correction slice, add separate exact-item tests: linked bilingual old/new values resolve by ID despite no equal words; stale revisions and partial/compound selectors do not traverse; unselected negated and unrelated facts remain byte-identical. Do not mark these future assertions as covered by creation-only acceptance.

## Controller decisions still open

| Decision | Recommendation and unresolved consequence |
| --- | --- |
| Storage/ownership and rollout | Choose the sidecar paths/schema, workspace namespace lifetime and retention budget. Implement both owner and Team storage or explicitly gate unsupported Team A writes. Choosing about.json v2 instead requires downgrade prevention and dual-version readers; do not guess deployment support. |
| Accepted-item granularity | First slice shares one frozen whole body, with no correction. Define the later host/UI/tool contract for a complete atomic item before enabling automatic correction. No syntactic heuristic can prove a model's compound sentence has one proposition. Independently paraphrased/translated existing facts remain unlinked. |
| Writer coverage | Choose conservative whole-document invalidation first, or assign verified relocation mappings to every relevant writer. Automatic organize runs immediately after capture, so ignoring it can invalidate newly created links at once; acceptance must measure/report that rather than suppress organize or claim stable coverage. |
| Retention/card eviction | Choose bounded active-edge retention and what happens after 200 desktop cards. Missing metadata must yield unresolved. Do not silently create permanent hidden history or tombstones. |
| Failure/status contract | Assign precise per-item outcomes and how capture status distinguishes notes-only/partial linkage. Decide whether inactive creation records are needed; neither crash recovery nor operation retry safety is already supplied by existing writes. |
| Transfer/downgrade | Choose explicit unsupported/unlinked behavior first, versus a separate versioned graph transport project. Receipt hashes cannot prove identity survived unsupported equal-byte ABA writes. Confirm backup privacy classification for new paths before enabling them. |
| Dream and replay | Keep dream and restored/old-source ambiguous work unlinked initially. A future dream synthesis may mint a **new** common accepted item from multiple sources; its `outdated` relation needs separate validation. Neither source IDs nor the current fence prove persistent semantic replay prevention. |

No decision here requires a new user approval screen: handles establish provenance under existing host authority; a model claiming an ID cannot enlarge that authority.

## Non-goals, review and validation

No legacy backfill, cross-person read, semantic/LLM/substring association, auto-translation, compound-fact splitting, global suppression/tombstone reuse, universal forgetting, historical deletion, journal/backup rewriting, arbitrary filesystem tamper resistance, cross-process CAS, ABA detection, cross-file transaction, crash replay recovery or installed-product claim. This design does not close the original automatic legacy case or prevent every future helper from relearning stale meaning.

Scoped maintenance/security review: this delivery adds documentation only. The proposal keeps source identity in host-owned person state, preserves existing audience/fence/secret boundaries, separates provenance from authority and treats missing/partial metadata as unresolved. No dependency, permission, external request, process capability or deletion policy changes. The principal new maintenance obligations are schema validation, writer invalidation, bounded edge retention and transport privacy; they need explicit implementation ownership.

Validation for this research is source inspection plus local Markdown/source-anchor/index/whitespace and changed-file-scope checks. No product test or synthetic implementation probe was run; the bounded negative test above is a specification. Historical tests and controller acceptance are cited as prior evidence only. This is a design handoff for controller review, not implementation approval or integration.
