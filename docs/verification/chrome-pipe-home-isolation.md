# Pipe Chrome fixture HOME isolation

The pipe verification helper must preserve the caller's synthetic home. The baseline default read `userInfo().homedir`, which consults the account database rather than the fixture's HOME. A temporary Chrome profile alone did not prevent that environment override.

`chromeLaunchEnv` now defaults to the supplied environment's HOME, or USERPROFILE for win32. An absent or empty variable stays absent or empty; the helper never fills it from the account database. Callers must still supply a synthetic home: this change does not guarantee Chrome's own behavior when HOME is absent. The third argument remains an explicit home override, including a deliberately selected account home. Arguments, temporary-profile allocation, credential-store flags and egress policy are unchanged.

## Reproduction and evidence

The focused regression is `server/testing/chrome-pipe.test.ts`. Before the product change, the new contract produced **7 failed / 3 passed**: inherited synthetic HOME/USERPROFILE, omitted arguments and absent-home cases failed. The explicit override and credential flags controls passed. The red source and patch were retained before modifying the helper.

Private evidence is in the controller workspace at `private/engineering-foundation-evidence/f2-chrome-home-isolation/`. Each command has before/after source, selected dependency package contents/lock, Node, Chrome executable and runner hashes, exact argv, minimal environment, UTC, exit and persistent log. The snapshots include all tracked source/assets and untracked source files; dependency binding covers the runner/tool packages listed in the manifest, not every transitive installed byte. This is local evidence, not the F2 authoritative producer or a trust-map implementation.

The owned smoke uses the actual helper under synthetic HOME/USERPROFILE and a throwaway profile under tmpdir. A tiny owned executable records only HOME/USERPROFILE/argv/PID immediately before `execv` of installed Chrome, inheriting the same environment and pipe descriptors. A process listing confirms the executable; a CDP evaluation returns 42. A deny-all existing egress gate and the unchanged macOS mock-keychain argument remain active. The red smoke confirms the passed HOME equals the real account home and differs from the synthetic caller home; the green smoke requires equality with synthetic HOME. Both require profile removal and no remaining process referencing that profile after close.

Two initial red smoke attempts failed in the evidence harness's attempt to read HOME from `ps` output; the recorded exec environment already showed the mismatch. The probe was corrected within two repair rounds to use the exact exec environment, actual executable and CDP response. Both failed logs remain. They do not count as completed smoke acceptance. No Keychain access audit was performed, and no real Keychain read or absence-of-access guarantee is claimed.

Final related suites, guards, scoped strict types and lint are recorded in the private receipts on frozen source. There is no build, app installation, dependency acquisition, provider/model call or release action. Independent review is required before integration; the final integrated source needs its own regression run. This closes only the pipe helper's HOME precondition.

## Callers and other account-home paths

All `launchPipeChrome` / `chromeLaunchEnv` references were inspected:

- `launchPipeChrome`'s omitted-environment default invokes this helper and is the repaired path.
- Four launches in `server/browser/egress/hostile-pages.e2e.test.ts` and one in `server/use-my-mac.e2e.test.ts` already pass the synthetic `process.env` directly; no account-home override occurs there.
- `server/cloud-lending-chrome.e2e.test.ts` explicitly supplies its owned temporary home as the third argument. That override remains supported.
- The helper tests cover defaults, both platform variables, no account fallback and explicit overrides. No caller relies on the helper's old implicit real-home default.

Other findings are follow-ups, left unchanged:

- `server/browser/chrome/flags.ts`: `accountHome()` reads `userInfo().homedir`; `chromeEnv` deliberately defaults to it. `launchChrome` and calibration callers without an explicit home can therefore override synthetic HOME. Existing flags/calibration tests protect that production default; their account-home child is a known shell stand-in, not real Chrome. The production account-home policy is retained; fixture callers require an explicit owned home.
- `server/browser/chrome/launcher.ts`: private calibration/check environment and generated wrapper use `userInfo().homedir` by default on Darwin. Existing launcher tests explicitly protect this behavior using stand-ins. The server fixture now supplies an explicit owned `home` as described below; the production default and deliberate account-home stand-in tests remain unchanged.
- `server/drivers/muse-code.live.test.ts`: deliberately restores real account HOME for a signed-in live CLI, behind `OMB_LIVE_MUSE=1`. It is not an offline fixture; retain its opt-in and exclude it from synthetic/live-disabled acceptance. It was not run.

The existing CDP real-Chrome helper, bare-Chrome helper, hold-Chrome helper, real browser service, identity/passkey verification and manual browser verification supply an explicit synthetic home. Ordinary `os.homedir()` uses (including fake-engine fallbacks and product/browser resolver fallbacks) follow HOME/USERPROFILE at call time; the server test setup assigns those variables before imports. Helpers inheriting the parent environment still require a synthetic supervisor environment; a temporary profile by itself is insufficient.

## Fixture server launcher and backend

The subsequent policy audit found an additional reachable override: `launchVerificationServer` with full Chrome enters `index.ts`'s global launcher startup, whose calibration, generated wrapper and executable check previously received no explicit home. The server's synthetic HOME alone did not isolate those children. The full-Chrome cases in `scripts/testing/browser-evidence.e2e.test.ts` and `server/browser-navigation-stop.e2e.test.ts` use this topology. A named headless-shell selects the legacy plan and never enters this calibration/wrapper route.

`verificationServerEnvironment` now supplies `OMB_TEST_BROWSER_HOME` from its own disposable data directory, ignoring the parent's value. The global launcher and the browser host's ChromeEngine pass that value as the existing explicit `home` option. ChromeEngine already propagates it to its launcher and LocalBackend. Restarts retain the same fixture-owned home. No production account-home fallback, flags, calibration policy or explicit-home precedence changes; an ordinary server with no fixture override retains its previous behavior.

The added `scripts/testing/fixture-server-browser-home.test.ts` runs real fixture servers and records HOME, USERPROFILE, argv, PID and parent PID in owned child executables. Before the wiring change, three assertions failed: no fixture override, calibration child HOME equal to the account home, and generated-wrapper `--version` child HOME equal to the account home. The first command used the temporary test filename `scripts/testing/browser-fixture-home.test.ts`; the existing file of that name was restored byte-for-byte before the green run and its original three tests remain part of acceptance. Calibration's recorder deliberately exits before any Chrome execution. A separate cached synthetic identity lets the actual generated wrapper exec its recorder for `--version`, including after server restart. These are server-child stand-ins, not real full-Chrome proof. `server/host/browser-fixture-home.test.ts` verifies both fixture and absent-override construction through the real ChromeEngine to LocalBackend and launcher; existing backend launch tests retain the explicit-home boundary assertions.

For full-Chrome acceptance, set `OMB_FIXTURE_HOME_CHROME` to an explicitly approved owned full-Chrome executable (and optionally `OMB_FIXTURE_HOME_BINARY` to the approved agent-browser). The conditional case rejects headless-shell paths, execs the selected binary behind the same recorder, and requires both actual calibration and wrapper `--version` records with fixture HOME, parent PID and credential-store argv. It does not download a browser. This case is **not executed locally**: the accepted `local-acceptance-d075fdf4a/dist-native/browser/darwin-arm64` assets contain only headless-shell. The installed system Chrome was not substituted. Local browser-evidence and navigation-stop acceptance therefore exercise the legacy shell path, not full-Chrome calibration. Windows/Linux runtime isolation and the native ChromeEngine backend process are not established by the Darwin stand-in/construction evidence.
