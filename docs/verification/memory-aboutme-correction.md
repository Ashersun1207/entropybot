## Contract and choice

Choose **(a), replace the matched complete fact in place**, retaining its learned-by prefix/date (or handwritten bullet). After a successful `replace` or `supersede` note update, an authorized About me target corrects every line whose complete fact equals `oldText` under existing `foldForMatch` and `passageMatcher`. Matching excludes provenance and headings. Duplicate complete facts are all corrected; unmatched, partial, compound and longer-word facts remain byte-for-byte intact. Other bots' learned lines can be corrected without changing their original attribution. No semantic inference is attempted.

A partial passage alone cannot safely identify how much of a compound About me fact to replace. This contract deliberately requires the complete old fact, including punctuation; partial passages, alternate wording, note headers included in oldText and bundled unrelated facts are outside automatic correction. Such a note update can still succeed without changing About me. Multiline replacements, replacements longer than the existing learned-fact limit of 300 characters, and oldText containing a line break also stay notes-only. No new response fields or schema are introduced. This is a bounded qualification, not a claim to resolve every phrasing of the incoming real-model finding.

Option **(b), remove matching lines and record forget suppression**, is not chosen: existing suppression matches passages globally, can block a legitimate new value containing the old passage, and carries no person key. Reusing it for corrections could affect another member's learning; dropping a whole partially matched line can also delete unrelated facts. The synthetic replacement-containing-old-passage and Team Cloud cases preserve those boundaries. Corrections create no tombstones/suppression. Explicit append/prefer and forget remain on their existing paths.

`profile-learned.ts` has one necessary helper: after the desktop profile save, update only learned records whose exact prior line was changed, retaining ID, bot identity and timestamp. Otherwise a learned card's existing remove operation would search for its stale old line and leave the corrected fact behind. The fixture removes the corrected card through the production operation. The Team Cloud path continues to use `aboutMe.person`/`teamHost.learnAbout`; its existing learning path does not commit desktop learned cards, and correction does not touch that global file.

## Maintenance, security and limits

Scoped review covers update validation/write order, About me attribution/matching, desktop learned-card removal and Team Cloud person projection. The existing same-week concentrated review is in the engineering maintenance log. No new network requests, processes, credentials, dependencies, permissions, arbitrary deletion, history/journal/backup traversal or suppression policy are introduced. Existing memory-layer e2e uses disposable fake-engine/loopback infrastructure; the new fixture itself uses no HTTP or real model. Static wiring at the server caller remains unchanged.

The note, profile and learned-card files are not one atomic transaction. A failed profile save follows an already successful note write; a failed learned-card save can follow a successful profile save. No cross-file rollback, concurrency protocol or silent retry is added. Manual recovery and broader correction matching need separate scope. Same corrected text is idempotent for profile/card bytes. Duplicate corrected values can retain duplicate lines rather than deleting their provenance.

This does not qualify semantic/paraphrased corrections, partial facts, raw historical source removal, capture races, restore/import, physical erasure, real-model judgement, installed UI, remote CI or cross-platform behavior. The controller must assess whether the complete-literal-fact boundary is sufficient for the incoming finding; broader matching requires a separately scoped contract.
