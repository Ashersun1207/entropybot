## Contract

For `memory_update` replace/supersede, the optional pair `old_about_me_text` / `about_me_text` selects one complete exact current profile line (including its original prefix) and supplies its complete replacement fact body. The driver maps this to `oldAboutMeText` / `aboutMeText`. It uses the existing owner's own ask / server-derived Team person authorization. The bot already sees that person's current About me in its ordinary prompt. No new model, semantic matching helper, cross-person read, manual approval/token, settings cleanup or persistent correction state is introduced.

The pair is validated before notes change: both strings, supported action, nonblank single lines, old line at most 24,000 characters and new body at most 300. Notes update first. An authorized profile edit then requires exactly one complete byte-identical old line in the freshly read profile, with no await through saving. Preserve its actual learned-by/date or bullet prefix, unrelated lines and desktop learned-card ID/bot/time. Duplicate, absent/changed, heading, empty-body or unsupported targets do not write profile. The new body is explicit; preserve unrelated clauses in compound facts. No substring/normalization/translation fallback or bulk deduplication occurs. Team checked saves cannot silently trim/truncate the planned value.

This is a value compare-and-swap within the synchronous server path, not cross-process CAS or immutable item identity. Unrelated newer lines survive because planning uses the current profile. Identical ABA bytes are accepted. The old selector itself is not independent permission; `opts.aboutMe:null` and Team room/shared scopes cannot gain profile authority by supplying the pair. Existing externally approved writes remain notes-only.

Successful notes retain their existing HTTP result fields, with an additive `aboutMeCorrection` outcome: `not_checked`, `refused`, `conflict`, `saved` or `partial`, using fixed reasons. Missing pair means notes-only/not_checked; it no longer triggers the earlier candidate's implicit literal correction. Driver text distinguishes saved notes from an unresolved profile, and an old server returning no profile outcome is explicitly unconfirmed. Forget/prefer/append/remove semantics remain on their original branches.

Profile/card/notification failures do not repeat note writes or roll back whole documents. Notes may have committed before a profile failure; a corrected profile may survive a card-metadata failure. Notification failure is reported after known saved state. Persisted profile bytes are checked; failure/mismatch yields a partial result without raw error text. There is no cross-file transaction, automatic crash recovery or whole-operation retry-idempotence promise. After a partial/uncertain response, re-read state before attempting another action.

## Process-local per-person stale-work fence

`createAboutMe` holds counters keyed only by the server-derived desktop owner / Team person. A selected current profile correction invalidates that person's prior work before attempting save; partial save can conservatively invalidate it too. Different bots for the same person share the counter; another person is unaffected.

Capture stamps turns at enqueue/buffer entry, samples again before its helper and checks both snapshots after await before any filing or About me learning. Already queued turns are not restamped when the buffer flushes or the worker resumes. A stale entire call is refused before note/topic/card writes. Dream has its own pre-helper snapshot and pre-write check, covering both outdated notes and learned output. No global pause/stop and no per-person durable state is added. Stale work reports deferral and is not automatically replayed.

The fake delayed tests prove capture and dream rejection, queued/buffered work preservation of its old snapshot, cross-bot same-person invalidation, and another person's independent capture/dream success. NEW helper work started after correction can still read retained older sources and relearn even the exact old English fact; separate controls deliberately demonstrate that limitation. Restored pending turns now receive a fence immediately when loaded into the buffer and retain a restored-origin marker through flush: a correction later in this SAME process invalidates them. Their provenance before loading remains unverified; no persisted pre-restart fence is invented. There is no suppression identity store, semantic permanence, history/journal/backup deletion or all-copy erasure claim.
