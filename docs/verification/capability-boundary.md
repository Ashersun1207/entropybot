# L1: core and on-demand capability boundary

Research date: 2026-11-09. Owner: assigned L1 research subagent. Checkout: `/Users/sun/Desktop/Codex/gorkbot/.worktrees/l1-capability-boundary`, branch `codex/l1-capability-boundary`, baseline `183e1b21eebb30606ac7d544184183f2f0c438ff` (initial status clean). This is ordinary product research, not a development-quality ledger case or skill trial. Only this report and its README index link change.

**The current desktop package is a comprehensive offline resource bundle, not a small core with a general capability downloader.** `package:prepare` always stages Android tools, cloudflared, browser and DuckDB resources; platform packaging adds CUA and, on macOS, speech. Some capabilities start on use, some initialize earlier, and several additional runtimes download separately. Deferring a process, loading a module lazily, and excluding bytes from an installer are different boundaries.

This is static source research plus local file-size measurement. No build, installation, dependency resolution, download, push, fixture, model call, live app/data access or Keychain access was performed. Offline and failure behavior below describes code, not a newly executed acceptance test. The L1 plan's complete-download/first-use/offline/repair experiment and actual distribution validation remain unverified under the build restriction.

## Additional acquisition and core boundaries

The core for a local text conversation consists of the UI/desktop host (for desktop distribution), bundled server/Node runtime, local SQLite and Markdown persistence, authorization/approval/credential handling, orchestration, and at least one configured usable model route. **No particular external CLI, browser, DuckDB, device tool, tunnel or speech engine is intrinsically necessary for every text conversation.** Direct protocol providers can avoid a downloaded CLI; this is not a claim that real model service works without network.

Current coupling matters before deleting package resources:

- `electron/main.mjs` initializes CUA on ordinary local desktop startup; gate/progress/error state would need to distinguish not installed, disabled and failed.
- `server/index.ts::dataIntegration` calls `dataEngine.unavailable()` during turn preparation and omits data tools on failure. `Engine.load()` permanently caches a failed require for that process. A future install action needs explicit re-probe/restart semantics and honest tool availability, not optimistic capability advertisement. [C1's prior synthetic measurement](chat-prep-stage-attribution.md) attributed 53.568 ms median to this first-load branch; **this task did not repeat that measurement**, and size does not predict latency/RSS.
- DuckDB, chart rendering and 1Password share a packaging/require root, although they serve distinct features. Split ownership and discovery before making one optional package's removal affect all three.
- Electron includes Chromium for UI, the resource bundle includes headless shell, and macOS arm64 may additionally acquire full Chrome. These are three distinct distributions; Electron's browser is not automatically a supported automation substitute.
- Bundled companion, updater, enterprise module, MCP proxies, skills, static model catalog, noVNC and browser injection/vendor JS are separate build outputs or repository assets, **not first-use native downloads**. `bundle-server.mjs` copies/bundles them; enterprise is conditional on source presence/license. No extra local model downloader was identified in the examined packaging/runtime acquisition paths. User-directed shell tasks can install arbitrary programs; that open-ended behavior is not a fixed capability inventory.
- Organization/team packages and skill imports are optional content acquisition, not a fixed native runtime. `server/org-library*.ts`, `electron/org-library.mjs`, `server/team-library.ts` and `server/skill-fetch.ts` were search leads; no full trust review of content installers was done. They must retain their own authorization/review/provenance boundary if future capability packs reuse that transport.
- CUA exposes delegated tools such as `install_ffmpeg` (listed in `server/computer-tool-list.ts`). The vendor driver's implementation/source URL/hash and side-effect policy for that secondary acquisition are **unverified here**; it is not another app-pinned build asset. Likewise OS voices/speech assets, container-runtime VMs, external ACP/MCP packages and externally hosted Chatterbox models are outside the fixed resource manifest.

## Packaging assessment and recommendations

1. **Keep the text-chat substrate core; make computer, browser, data/connectors, voice and remote access explicit optional capabilities.** Preserve persistence/auth/approval/update and error handling locally. A usable model route is essential, but every provider's CLI does not need to ship. Do not add dependency downloads to normal startup or ordinary chat while making this split.
2. **Prioritize browser policy before attempting shell removal.** The browser shell archive alone is 99–120 MB; optional full Chrome adds 191 MB compressed on supported Mac first use, while Electron's existing reference distribution is 312 MB logical. Define which browser/backend is promised, how offline fallback is selected before a session, and whether both shell and full Chrome are needed. Removing the shell today would remove current offline coverage on platforms without a full-Chrome pin.
3. **Treat DuckDB and CUA as major native-resource candidates, with measured final slices still required.** Reference universal DuckDB is 117 MB and CUA SDK 53 MB before thinning, plus CUA CLI; these are significant but not final savings figures. Separate DuckDB, resvg (~3.5–3.9 MB) and 1Password WASM (~14 MB) resource ownership; add coherent unavailable/installing/ready/retry states and failure-cache reset before any future hot installation. Maintain correct tool advertisement and existing permissions.
4. **Pin ADB before extending download reuse.** Replace mutable latest/versionless override trust in a future task with reviewed version, archive and executable integrity, bounded download/extraction, provenance/license and verified offline input. This is the clearest reproducibility gap in mandatory package preparation. No code change is proposed as already implemented here.
5. **Use one explicit install/repair contract for optional packs, without broadening privileges.** A future manifest should bind OS/CPU/ABI, version, source/allowed redirects, archive/member hashes, expanded size, licenses, compatible app range and signature provenance. Require bounded/cancellable download, atomic publish, verified reuse, repair without deleting profiles/data, offline import, retained valid prior version and clear failure recovery. Apply the same content identity to cross-CPU npm-pack assets and CUA cached/override programs. Installer permission is distinct from computer-control permission.
6. **Keep large provider and VM payloads deferred.** Antigravity is already 114–337 MB compressed and up to ~1.06 GB for the two Linux members; OpenCode standalone 64–82 MB compressed. VM image size is unknown but acquisition spans multiple upstreams. Report required disk space/download progress and explain cold offline limits. A warm cache is not evidence of cold offline support or repair resilience. Do not bundle all providers to avoid one upstream outage.
7. **Do not optimize tiny or OS-owned voice assets as though they were model bundles.** The helper measured only 0.26 MB; this app does not download a local TTS model. Clarify actual Apple on-device/network behavior and OS language-asset availability before making privacy/offline promises. Cloud TTS service availability cannot be repaired by reinstalling a native pack.
8. **Next authorized experiment should measure behavior and final resource contribution separately.** Once separately authorized, use synthetic isolated homes and already available verified assets to compare full/cold/missing/corrupt/partial/offline/restart/repair paths and cancellation. Record compressed transfer, expanded resource bytes, peak temporary disk, first usable capability latency and process/RSS separately. Cover all target architectures and preserve profile/credential boundaries. This report neither authorizes packaging nor supplies distribution acceptance evidence.

Largest currently bundled contributors supported by evidence are Electron's shell distribution and the optional browser/native resource classes; exact rank among expanded browser, thinned DuckDB and CUA CLI+SDK is **unverified**. Largest numerically documented deferred payloads are Antigravity and full Chrome, followed by standalone OpenCode; VM layers and provider-specific npm content cannot be ranked without additional local assets. cloudflared's “40 MB” and Caddy's “15 MB” are source estimates only. There is no defensible total installer savings percentage from this study.
