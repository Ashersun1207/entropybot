## Product path

Open the actual **Automations** page, choose **New → Manual web collection**, enter a name, choose an existing bot and enter one complete HTTP/S URL per line. The alternate **Set up yourself** menu contains the same explicit collection type. No model is needed to create or run this type.

The editor uses the existing BotPicker, modal styles and useBotEditor POST/PATCH transport. Input is finite (1–100 nonblank lines; 8192 characters per URL), rejects malformed URLs, credentials, whitespace, backslashes and markup, removes fragments, and preserves duplicate entries. It never truncates a list. New plans have the typed `web-collection` kind, version 1, page/attempt limits equal to the list length, 1 MB per page, 10 MB cumulative and 30 seconds. Edits preserve the saved limits and reject a larger list that exceeds them. Existing schedule metadata stays present but disabled; collections always save `enabled:false`, `runOn:maus`, `target:bot`, with no checks, startup, continuity, brief delivery or attachments. Saving sends no run request. There are no time/cloud/room/check controls for collection. Ordinary editors remain unchanged apart from extracting their original BotPicker into a shared focused component.

A collection row opens the actual EventDetails, including its existing protected manual action, exact submitted run, uncertainty explanation, Retry, acknowledged replacement and recent history controls. Collection details and rows omit enable/resume controls. Run output is projected to page/unique counts and report availability without showing the server path. No legacy run fallback or automatic recovery POST was added.

The report child only reads the authorized `/api/routines/:routineId/runs/:runId/collection-report` route on an explicit View report click. Its runtime validator imports the accepted shared `CollectionReportResponse`; this owner does not create or edit the shared type. HTTP 404 and the route's explicit unavailable code map to the fixed missing-report message; 401/403 map to denied; invalid 409 maps to unverifiable. Responses are scoped by exact run, cancelled on unmount, shape/count/hash checked, and rendered as escaped plain text in collapsed source sections. Each source preview is capped at 20,000 characters with a visible notice. No Markdown, HTML, image, active link, server path fetch, arbitrary source fetch or file opening is used by this child. Missing, denied, unverifiable and general load errors use distinct fixed localized text. Report-fetch unit tests use synthetic transport and do not qualify the server endpoint.

## P2 independent-review correction, round 1: bound response bytes before parsing

Review of `4085f0478f690f148acbcf124858dd4256dabc30` found that the report used generic `api()` and its unbounded `Response.json()` before the shape validator. The 20,000-character display preview and post-parse source checks did not bound response allocation. `p2-r1-red` runs the complete CollectionUI suite on the original pipeline with a new oversized Content-Length regression: 23 passed / one failed, with the actual JSON response parser called once. Earlier browser/server evidence remains bound only to the pre-correction source.

The correction keeps the existing API transport and request options, adding an opt-in `responseByteLimit`. Unrelated calls retain their original parser and fallback; limited background reads do not coalesce with unlimited reads. `fetchCollectionReport` pins a fixed 62,000,000-byte ceiling and the existing 15-second timeout. The server accepts at most 61,000,000 artifact bytes; its compact public response replaces private binding metadata with hash/unique fields and a small JSON envelope, so the extra 1,000,000 bytes cover that envelope. This is a response-byte ceiling, separate from source text and preview limits. No sources are silently truncated.

`readBoundedJson` rejects oversized or invalid declared lengths immediately and counts every actual streamed byte even when Content-Length is missing or low. It rejects uncompressed length mismatches. Fetch transparently decodes compressed responses, so an encoded Content-Length is not compared to decoded length; decoded bytes still have the same hard ceiling. A capped, geometrically grown byte buffer avoids retaining an unbounded list of tiny chunks. UTF-8 decoding is fatal and happens only after the complete body fits; JSON.parse follows it. Excess bytes and invalid UTF-8 cannot reach JSON.parse. Error/abort paths cancel the body reader, remove the abort listener and release its lock; cancellation does not wait indefinitely for a producer's cancellation promise. The same combined caller/timeout signal covers fetch and body reads. Exact-run keys, auth/desktop headers, credentials, HTTP refusal handling and fixed localized errors remain in the existing transport. Size/encoding/JSON failures use the existing unverifiable-report message; other errors retain their original mappings.

Focused complete regressions are `src/lib/bounded-json.test.ts`, `src/state/api-bounded.test.ts`, existing `src/state/api-background.test.ts`, and `src/components/routines/CollectionUI.test.ts`. They include exact-boundary multibyte UTF-8 split across byte-sized and empty chunks, buffer growth without dropped rows/text, declared/missing/low lengths, oversized single and multiple chunks before parsing, actual 62 MB report-stream enforcement, invalid/truncated UTF-8, malformed JSON, in-flight partial-body abort, already-aborted callers, timeout, unmount/late results, refusal handling and unchanged ordinary API calls. Tests assert no JSON parse on oversized bodies and cancellation/unlocked readers. The initial strict typecheck caught an inferred optional header in a new test; a HeadersInit annotation fixes that test without changing compiler settings.
