# Protected manual routine frontend consumer

A1b5 is a bounded frontend candidate on baseline `1077ee7d0293427ce4b76e4579cf0e2c00afaa86`, sole writer in `engineering-protected-run-client`. Parent review and serial integration remain separate. This is a partial candidate and is not ready for integration until the catalog blocker and the storage-readback concern below are resolved.

StoreProvider routes its actual `runRoutine` action through `routine-run-intent.ts`. It reads the advertised protocol and strict authenticated session metadata without using the general session decoder's loopback fallback, captures scope before waiting for execution settings, then rechecks authoritative scope before POST. Only `/run-protected` is used. Both identity and context headers are mandatory. The server remains the final authority. There is no automatic retry or legacy fallback.

The origin's localStorage ledger uses version 1 and at most 32 entries / 32,000 input characters. Entries contain environment UUID, non-secret context, routine ID, random request UUID and pending/confirmed phase. They contain no credentials, profile, prompts or raw personal data. Pending entries are written and read back before dispatch. Confirmed entries may be evicted to make room; pending entries are never silently evicted. A corrupted, unavailable or unknown-version ledger blocks dispatch. Missing storage is not treated as an empty ledger when access fails.

A pending operation retains its key and captured context across retry and provider remount. Unknown delivery, HTTP refusals, invalid JSON and missing or contradictory run provenance do not close it. A valid decoded run closes the operation only after confirmed persistence succeeds; a failed confirmed write retains uncertainty in the tested setItem-failure case. The write-succeeded/readback-failed case remains a blocking self-review concern described below. In-flight calls share one promise while each StoreProvider action receives its own success/error and settled callbacks. Browser cancellation is never described as server cancellation. A context mismatch preserves the prior marker and blocks replay. Routine details offers Retry and Start another run; the latter requires a confirmation explicitly acknowledging possible prior execution and no cancellation. A normal run has no extra confirmation. Cloud setup displays the protected operation's plain error text, and automation actions already propagate store errors.

Catalog blocker: English and Chinese have five new keys. The existing check requires pt-br to be complete and reports those five entries missing. Its sameAsEnglish allowlist is for intentionally unchanged names/codes, not untranslated recovery prose. Adding invented Portuguese or weakening completeness is outside this task. Parent must arrange reviewed Portuguese text and the existing catalog acceptance/hash workflow, or explicitly authorize a different established fallback policy. Neither the checker nor its policy is modified here. Other incomplete catalogs use the existing English fallback.

Storage-readback concern (code review, not yet executable evidence): if the confirmed setItem succeeds and its immediate getItem fails, the call returns unknown while the ledger may already say confirmed. A later call in the same provider currently permits that confirmed record to select a fresh key despite the retained in-memory uncertainty. The next bounded task must inject that exact read failure, preserve a red result, and ensure retry conservatively retains the previous key/context until confirmation is delivered or explicitly acknowledged. Do not integrate this candidate with that concern unresolved. This is separate from the tested confirmed setItem failure.

The final batch before the slow-preflight correction passed 93 tests across the protected helper/provider, routine details compatibility, CloudSetup and size guard; frontend typecheck and focused lint passed, i18n failed with exactly the five missing pt-br keys. ## Maintenance and security review

No dependencies, scripts in the product, backend, protocol, runner, CI, policy or size budget changed. StoreProvider retains the settings barrier and delegates actual intent ownership to one focused helper. New network traffic is same-origin, no-store metadata GETs and the protected manual POST, with a bounded POST timeout. Persistent context is an equality guard, never a credential or authorization grant. Unknown operations remain visible and recoverable. The catalog failure prevents a completion claim. Model wait and served-model identity are unknown; measured per-command elapsed time is in receipts. No build, install, push, remote CI, publication or parent integration occurred.
