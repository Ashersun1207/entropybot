# Protected manual routine frontend consumer

The [reload recovery follow-up](routine-run-reload-recovery.md) supersedes the historical provider-only recovery and confirmed-entry eviction semantics below. It adds actual browser reload/server restart evidence and conservatively reconciles stored confirmed markers in a fresh owner.

A1b5 is a bounded frontend candidate on baseline `1077ee7d0293427ce4b76e4579cf0e2c00afaa86`, sole writer in `engineering-protected-run-client`. Parent review and serial integration remain separate. The original partial candidate's storage-readback failure is addressed by the bounded R1 below and awaits parent re-review. The catalog blocker remains parent-owned; this task does not resolve or recheck i18n.

StoreProvider routes its actual `runRoutine` action through `routine-run-intent.ts`. It reads the advertised protocol and strict authenticated session metadata without using the general session decoder's loopback fallback, captures scope before waiting for execution settings, then rechecks authoritative scope before POST. Only `/run-protected` is used. Both identity and context headers are mandatory. The server remains the final authority. There is no automatic retry or legacy fallback.

The origin's localStorage ledger uses version 1 and at most 32 entries / 32,000 input characters. Entries contain environment UUID, non-secret context, routine ID, random request UUID and pending/confirmed phase. They contain no credentials, profile, prompts or raw personal data. Pending entries are written and read back before dispatch. Confirmed entries may be evicted to make room; pending entries are never silently evicted. A corrupted, unavailable or unknown-version ledger blocks dispatch. Missing storage is not treated as an empty ledger when access fails.

A pending operation retains its key and captured context across retry and provider remount. Unknown delivery, HTTP refusals, invalid JSON and missing or contradictory run provenance do not close it. A valid decoded run closes the operation only after confirmed persistence succeeds. A failed confirmed write or readback retains the provider's uncertainty, which takes precedence over a persisted confirmed phase on retry. The stored identity and scope must still match that held intent; storage corruption or replacement blocks replay. In-flight calls share one promise while each StoreProvider action receives its own success/error and settled callbacks. Browser cancellation is never described as server cancellation. A context mismatch preserves the prior marker and blocks replay. Routine details offers Retry and Start another run; the latter requires a confirmation explicitly acknowledging possible prior execution and no cancellation. A normal run has no extra confirmation. Cloud setup displays the protected operation's plain error text, and automation actions already propagate store errors.
